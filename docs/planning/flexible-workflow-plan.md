# 方案：柔性工作流（大流程卡死边界，阶段内放开路径）

> 2026-11-10。回答一个问题：**把研发交付流程从「每阶段一份操作清单」改成「卡死边界与验收、放开路径」该怎么落。**
> 状态：**M19–M23 已实现（2026-11-10）**，实施口径与偏离见文末「实施记录」。M19 可独立上线，M20 起含 DDL 变更（`KERNEL_VERSION = M20.0.0`，首启重建投影）。
> 关联：[SPEC-ai-workflow](../specs/SPEC-ai-workflow.md)（阶段语义与提示词段序）、[SPEC-review-handoff](../specs/SPEC-review-handoff.md)（findings 硬门与 artifacts 落盘）、[SPEC-task-fanout](../specs/SPEC-task-fanout.md)（D10「拆归 Agent、落点归内核」）、[ARCHITECTURE](../ARCHITECTURE.md)。

## 结论

现状的卡顿感不来自阶段数量，来自**把「怎么做」写成了指令、把「做完」留成了空白**。改法是三层分离：

| 层           | 内容                                                                  | 谁定          | 性质                             |
| ------------ | --------------------------------------------------------------------- | ------------- | -------------------------------- |
| **不变量**   | 派给谁 / 在哪跑 / 什么权限 / 落点阶段 / 子任务上限 / 不可逆动作要人批 | 内核硬规则    | 卡死，Agent 无权改               |
| **验收**     | 本阶段「做完」的可判定口径（命令退出码、清单条目）                    | 阶段配置 + 人 | 卡死，Agent 必须达成或给出理由   |
| **参考做法** | 小步提交、flag 包住、ADR 模板、拆几步、先做什么                       | 模板文案      | 放开，Agent 可偏离，但偏离要留痕 |

Agent 的自由度就产生在第三层：路径、顺序、拆法、办法全部自选；同时第一、二层把「跑偏到无法挽回」的口子焊死。

## 设计原则

- **P1 卡边界不卡步骤。** 一切约束必须能回答「不遵守会出什么不可挽回的事」；答不上来的约束降级为参考做法。
- **P2 完成判定不靠自评。** 「做完」必须落到可执行证据（`checks` 退出码）或可判定条目上。
- **P3 人只在四类点出现**：不可逆操作、口径缺失、越出边界、同一问题两轮未收敛。其余让人自己选。
- **P4 自由必须可审计。** 偏离、跳级、未达项都要留痕（评论 / 回执 / 标签），可事后复核——`run.approvals` 已是这个先例。
- **P5 先放后收。** 先放开，用指标看到哪条线崩了再收紧那一处；顺序反了就是全流程瘫痪。

## 现状诊断（四处「死」）

| #   | 症状                                   | 证据                                                                                                                 | 后果                                                                                  |
| --- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 1   | 阶段说明是过程指令清单                 | [sop-templates.ts:168-173](../../src/renderer/src/apps/ai-workflow/model/sop-templates.ts:168)「编码实现」四条硬要求 | 清单外的情况只能硬凑或停下问                                                          |
| 2   | 出口只有「run 正常结束」，没有完成口径 | [prompt.ts:69-89](../../src/kernel/prompt.ts:69) 段序里没有验收段                                                    | 「做完」= 模型自己说完了                                                              |
| 3   | 人的位置固定成阶段类型                 | 研发交付模板「代码评审」`entryMode: 'user'`                                                                          | 人被迫每步看一眼，而非只在异常时出现                                                  |
| 4   | 拆解被做成独立阶段                     | 模板「任务拆解」                                                                                                     | 与 [SPEC-task-fanout D10](../specs/SPEC-task-fanout.md:43) 冲突：拆解本就是执行者的活 |

已有可复用的地基：闸门 + `checks[].exitCode`（M11）、`findings[] / addresses[]` 硬门（M14）、`spawn[]` 拆解原语（M8）、artifacts 落盘（M16）、跨工作流 `handoff`（M7）。本方案不新造机制，只把这几块从「只在闸门/评审里生效」扩到「每个阶段都可用」。

## 设计决策

| 编号   | 决策                                                                                                  | 理由 / 取舍                                                                                                                                         |
| ------ | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D1** | 阶段说明统一成四段式 `### 目标 / ### 产出 / ### 验收 / ### 边界`，原清单降级为「参考做法」子段        | 零字段、零 DDL，改文案即可生效；面板里用三级标题，外层 `## 阶段要做什么` 段头不变，老提示词逐字不变的口径不被破坏                                   |
| **D2** | `WorkflowStage` 新增 `acceptance: string[]`（0–12 条，每条 ≤200 码点），独立成段拼进提示词            | 验收成为字段才能被闸门复用、被 UI 收敛展示、被 M21 判定；纯文本验收无法机检                                                                         |
| **D3** | 阶段新增 `maxRounds`（1–5，null = 1）：run 结束但验收未全达且轮数未超 → **原地续一轮**，不流转        | 现在这种情况要人点「重新执行」，等于把 agent 的 inner loop 外包给人；轮数用视图派生，不改 `runs` 表                                                 |
| **D4** | 新增固定提示词段「打断规则」：只有四类触发点发 `ask`，其余自己决定                                    | 放开路径后最大的失败模式是 ask 泛滥；用固定文案（同事实同文本）而非可配开关，避免每阶段重写                                                         |
| **D5** | 研发交付模板 6 阶段 → 5：澄清 → 实现（可 spawn）→ 评审（agent 闸门）→ 人工验收 → 收尾；删「任务拆解」 | 拆解交给 `spawn`；人工阶段只保留一处，且放在评审之后而不是中间                                                                                      |
| **D6** | 段间交接按**引用**：上一阶段给 artifacts 路径 + 契约，不给正文摘要                                    | 摘要会截断结论（[thread-context.ts:109-127](../../src/kernel/thread-context.ts:109) 现已按 2000 码点截断）；给路径让 Agent 按需读，上下文自然空出来 |
| **D7** | 人工跳级（`MOVE_TO` 非自然流转）自动追加一条 `author='host'` 的任务评论                               | 有审计的自由才能收回（P4）；跳级现在是静默的                                                                                                        |
| **D8** | 新增只读派生视图 `stageMetrics`：每阶段 run 数、平均轮数、自修复耗尽率、degraded 率、ask 数           | 先放后收（P5）的依据；不改 schema，从投影现算                                                                                                       |

### D1 四段式（M19，零内核）

模板统一形状：

```md
### 目标

让 <feature> 在主干上可运行，默认关闭。

### 产出

- 代码：短分支 → PR，说明写清改了什么
- 证据：`pnpm check` 输出、新增测试文件路径

### 验收

- `pnpm check` 退出码 0
- Given/When/Then 每条都有测试覆盖
- 无 flag 时线上行为与改动前一致

### 边界

- 不动 <模块>、不改 schema
- 参考做法（可合并、可跳过，只要验收达成）：小步提交、Conventional Commits、flag 包住
- 拿不准的选型：发一张 ask 卡，别猜
```

细则：

- `prompt.ts` 的 `stageInstructionsText` 不改文案，只由模板提供三级标题；无验收也无 instructions 的老工作流提示词逐字不变（[prompt.ts:95-100](../../src/kernel/prompt.ts:95) 的空值口径不破）。
- `WorkflowEditor` 的「要干什么」输入框加这段占位模板；保存时若正文非空且不含「### 验收」，在弹窗内给**软提示**（不阻断），因为老工作流合法。
- 字数软上限：四段各 ≤300 字，超出只提示（提示词预算有限，但不该拿校验卡人）。

### D2 `acceptance` 字段（M20，DDL 变）

```ts
// protocol/entities.ts
export interface WorkflowStage {
  // …既有…
  /** M20：本阶段「做完」的可判定条目（0–12 条，每条 ≤200 码点）；空数组 = 未声明 */
  acceptance?: readonly string[]
}
export interface StageInput {
  acceptance?: readonly string[]
}
```

- DDL 按既有补列模式（[schema.ts:788-796](../../src/host/schema.ts:788)）：`STAGES_M20_ADDED_COLUMNS = ['acceptance_json']`，语句 `ALTER TABLE workflow_stages ADD COLUMN acceptance_json TEXT NOT NULL DEFAULT '[]'`；`KERNEL_VERSION` 升 `M20.0.0` → 首启全量重建投影（DDL 进指纹）。
- 归一：老事实缺 `acceptance` → `[]`（同 `instructions` 的归一位置）；`[]` 不产提示词段。
- 提示词段序（插在「阶段要做什么」之后、「闸门判定」之前）：

```
systemPrompt → 任务 → 描述 → 阶段 → 阶段要做什么 → 验收 → 闸门判定 → 打断规则 → 反馈 → 线程上下文 → 回执
```

- 闸门联动：闸门阶段且验收非空时，`gateInstructionsText` 追加一句「每条验收条目要么在 `checks` 里有对应命令与退出码，要么在正文说明为何无法机检」——只在两条件同时成立时追加，保持同事实同文本。
- 校验（[stage-validation.ts](../../src/kernel/workflow/stage-validation.ts)）：条数上限、空白条目丢弃、重复去重（归一不报错），越界报错文案沿用「阶段「X」的…」句式。
- UI 收敛：按 [SPEC-ai-workflow](../specs/SPEC-ai-workflow.md) 既有规则，`不交接` / `交给用户` 不展示验收；`交给智能体` / `闸门` 展示（一条一行）。

### D3 阶段内多轮自修复（M21）

回执新增键 `acceptance`（与 `checks` 同级、受 100 项/键上限约束）：

```json
{
  "acceptance": [
    { "no": 1, "met": true, "evidence": "pnpm check 退出码 0" },
    { "no": 3, "met": false, "note": "缺 E2E 覆盖" }
  ]
}
```

- `no` 是 1 基序号，对应 `acceptance` 数组下标；越界丢弃、缺项按**未达**处理（fail-closed）。
- 判定全达 → 按原规则流转（与 `verdict` 正交：验收是「本阶段自己做完了吗」，闸门是「业务上过没过」）。
- 未全达且 `round < maxRounds` → 同阶段产下一轮 `run.queued`（续接同一 `sessionId`），任务不流转；同时追加一条 `author='agent'` 评论：「第 N 轮自评：x/y 达成，未达：…」。
- 轮数**派生**：`view` 里按 `(taskId, stageId)` 数既有 stage run 条数，不新增 `runs` 列（沿用 [review-handoff D2](../specs/SPEC-review-handoff.md:48) 的口径：不扩 `RunRow` 契约、避免物理重建 `runs` 表）。
- 轮数用尽 → 正常流转 + 标签 `repair:exhausted` + 评论列未达项（人可见、可打回）。
- `run.status='failed'` 不消耗轮次，仍走「出错时进入」（与闸门预算同口径）。
- 护栏：只对 `entryMode==='agent'` 且 `acceptance.length>0` 生效；`maxRounds` 硬上限 5，防止烧 token。

### D4 打断规则（M19，零内核）

固定文案段，所有 agent 阶段出现（与是否闸门无关）：

```
## 打断规则（什么时候叫人）
只在四种情况**必须 ask**：
1. 不可逆动作，例如发布 / 删除 / 改生产数据 / 花钱 / 对外发信
2. 需求口径缺失且猜错返工成本高
3. 需要越出本阶段边界段
4. 同一问题连续两轮未收敛
其余可以先自己决定，拿不准再问我，不要为确认小事打断
```

（2026-11-11 按人改稿重写固定文案；「一轮只发一张 `ask`」不再写在这段里，改由回执块 `ask` 键口径统一管，见 `protocol/receipt-keys`。）

### D5 模板重排（M19）

研发交付：`需求澄清(agent)` → `编码实现(agent, spawnPolicy=agent)` → `代码评审(agent + 闸门, onFail=编码实现)` → `人工验收(user)` → `合并归档(agent)`。

- 删「任务拆解」；「技术方案」并入「需求澄清」的产出段（ADR 作为可选参考做法），或按需保留为独立阶段——默认删，网络效应小、卡顿感大。
- 其余五个模板同步四段式；「用户验证」「探索测试」「回顾会议」等本来就是人的阶段保持 `user`。
- 模板断言测试：每阶段 `instructions` 含四段头、`acceptance` 非空（用户/不交接阶段除外）。

### D6 段间按引用（M22）

- `precedingBlock` 从「最近一轮产出的 2000 码点摘要」改为「上一阶段 run 的 artifacts 路径 + 该轮验收结论摘要（短）」；执行器不可读文件时（[SPEC-review-handoff D15](../specs/SPEC-review-handoff.md:61) 已能判定）退回摘要。
- 路径形如 `<userData>/artifacts/threads/<threadId>/runs/<runId>/output.md`；只给路径与「读哪一段」，不贴全文。
- 收益：结论不再被单端截断；上下文预算留给本阶段。

### D7 跳转留痕（M22）

`MOVE_TO` 若落点不等于 `on_complete` 解析结果（含跨阶段前跳/后退），追加 `author='host'` 评论：「人工跳转：A → B（默认去向 C）」。不改转移公式，只加留痕。

### D8 指标（M23）

只读视图 `stageMetrics.byWorkflow`，字段：`runs` / `avgRounds` / `repairExhausted` / `degraded` / `asks` / `humanComments`。全部由 `runs` / `cards` / `task_comments` / 标签派生出，不新增投影表。设置 → 工作流 → 只读小表；无数据时显示「还没有运行数据」。

## 验收标准

每个里程碑：

- `pnpm check` 绿（typecheck + lint + coverage 阈值不降）。
- **老工作流提示词逐字不变**：无 `instructions` / 无 `acceptance` 的阶段，`taskPrompt` 输出与改动前完全一致（`tests/kernel/prompt.test.ts` 加对照用例）。
- M20 起：事实重放后 17 张投影表等价（含新列默认值），重建幂等。
- 每条新增字段有校验用例：越界、重复、空白、超长。

整体（可以称「松绑成功」的样子）：

- 同一条「实现某功能」任务在研发交付模板下：Agent 在一阶段内自己决定拆法/顺序/办法，中途不打断；人只在评审打回与最终验收被叫到，**人工介入 ≤2 次**（现状 ≥4 次）。
- 出现 ask 卡时，内容是**决策**（走 A 还是 B、要不要动生产），不是**确认**（我这样对吗）。
- 每次人工介入都能在任务动态里看到理由与影响范围。

## 风险与对策

| 风险           | 表现                     | 对策                                                                                              |
| -------------- | ------------------------ | ------------------------------------------------------------------------------------------------- |
| 自评放水       | 「都达成了」但仍不可用   | 验收条目必须对应 `checks` 退出码；闸门 `fail` 预算照旧；`repair:exhausted` / `gate:degraded` 可查 |
| ask 泛滥       | 每轮都问，比原来更烦     | D4 固定文案 + 「禁止为小事打断」+ M23 指标 `asks/run` 监控                                        |
| 提示词变长     | 四段 + 验收把上下文挤满  | 各段 300 字软上限；D6 按引用替代全文                                                              |
| 续轮烧钱       | 5 轮 × 大模型            | `maxRounds ≤5`、只在 `acceptance` 非空时启用、`runs.usage` 已记录可统计                           |
| 收紧惯性       | 出事就加约束，回到老样子 | 只收紧**不变量**层；参考做法层不动；每次收紧记一条理由到模板注释                                  |
| 模板变成新教条 | 四段式又被当成 checklist | 模板只是起点，`WorkflowEditor` 允许改；验收可达成就够                                             |

## 不做

- 不改 `entryMode` 三态（`none` / `agent` / `user`）与 `stage-machine` 的转移公式。
- 不引入「阶段自动生成」——那会让 SOP 不可审计、不可复盘。
- 不加新投影表（`stageMetrics` 是派生视图）。
- 不做多智能体协商 / 投票——单写者、单 agent 的原则先守住。
- 不把 `acceptance` 塞进 `review_reports`（会污染 findings 的跨阶段硬门语义）。

## 一句话

**边界卡死、验收卡死、路径放开。** M19 三个文案改动就能拿到大半收益，M20/M21 才需要动契约。

### 与方案的偏离（都以「不破坏既有不变量」为准）

1. **D7 的评论作者**：`TaskComment.author` 只有 `owner` / `agent`，跳转留痕用 `agent`（与 `gate:degraded` 的留痕同口径），没有新增作者枚举。
2. **续轮的提示词**：没有新写「继续」提示词，直接复用 `entryRunFacts`（同阶段再来一轮，全量阶段说明 + 验收 + 上轮自评评论作资料段）。少一个提示词入口 = 少一处漂移。
3. **续轮的会话回填**：`taskSessions` 只认终态 run，而本轮的结算事实与续轮在同一批里，所以显式把本轮 `sessionId` 写进新 run 的 `resumeSessionId`——否则多轮之间会丢上下文。
4. **轮数用尽不打标签**：`repair:exhausted` 需要改任务行，会和同批的 `task.moved` 互相覆盖；改为只在评论里写清「已达上限、按原规则流转」。
5. **D6 只在配了 `artifactsRoot` 时生效**：没配产物目录时退回原长摘要（否则模型既看不到全文、也没路径可读），老路径提示词逐字不变。
6. **编辑器字段收敛沿用 M18 规则**：`不交接` / `交给用户` 不展示验收与轮次，保存时归一到空。
