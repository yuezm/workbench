# 性能基线（PERF）

> 仪器：`node scripts/bench.mjs [--facts=100000] [--tasks=5000] [--samples=200] [--json]`
> 口径与「别拿它当压测」的边界见脚本头注释：每条写入单独提交并落盘，装载按 `viewSpec` 切片，重建从事实日志全量 fold。

## 怎么跑

```bash
node scripts/bench.mjs                                  # 默认 10 万事实 / 5000 任务 / 200 采样
node scripts/bench.mjs --facts=20000 --tasks=1000 --samples=50
node scripts/bench.mjs --json                           # 机器可读，便于对比历史
```

脚本自己造库、自己删临时目录，不碰 `userData`。仓库当前没有 CI 工作流，nightly 留待 CI 立项后再接。

## 基线（2026-11-14，本机 Windows / Node 22.22 / SQLite WAL + synchronous）

| 指标                               | 实测    |
| ---------------------------------- | ------- |
| 事实条数                           | 100,000 |
| 任务数                             | 5,000   |
| 造数耗时（批量事务）               | 1.2 s   |
| 装载 + decide（`task.comment`）p50 | 4.0 ms  |
| 装载 + decide（`task.comment`）p99 | 8.0 ms  |
| 装载 + tick（`clock.tick`）p50     | 0.5 ms  |
| 装载 + tick（`clock.tick`）p99     | 1.2 ms  |
| 全量重建                           | 1.45 s  |
| 启动增量（投影已最新）             | 0.1 ms  |
| 库体积                             | 60.5 MB |

p99 为 200 采样口径；三次 200 采样实测 decide p99 为 6.1 / 8.0 / 8.0 ms（取中位 8.0）。

## 读法与已知差距

- **整表 `tasks` 装载已改为按需装载**（2026-11-14）：此前每次决策把切片里的 `tasks` 整表（5000 行）读进视图（≈40 ms），是 `装载 + decide` 的主要成本。现在 `View.tasks` 是惰性 Map——`get` / `has` 按 id 单行查库，只有全量遍历（`size` / `values` / `keys` / `entries` / `forEach` / 迭代器）才整表装载。决策语义不变，`装载 + decide` 从 p50 47.3 ms / p99 56.0 ms 降到 p50 4.0 ms / p99 8.0 ms，tick 从 p50 45.4 / p99 51.1 降到 0.5 / 1.2 ms。
- **p99 剩余尾部是逐条提交的 fsync 抖动，不是装载或计算**：脚本每条写入单独提交并落盘，p50 4 ms 已远低于验收表的 8 ms；p99 随系统 fsync 抖动在 6–10 ms 摆动（500 采样实测 10.1 ms）。
- **评论切片随样本增长是已知异常**：`task.comment` 每个样本新增一行评论，`task_comments` 切片会随样本线性变大（9.5 万条时 p50 从 47 ms 涨到 430 ms 是这条切片本身的形状问题，不是回归）。基线固定 200 采样，就是为了不把这条异常当常态；若要进一步收敛，可把评论 / 评审等按 taskId 访问的切片也做按需装载（不在本次改动内）。
- **启动增量 0.1 ms** 与 **重建 1.45 s** 都在 ARCHITECTURE 验收表口径内（`<100 ms`、`<5 s`）。
- **造数必须放进一个事务**：WAL + synchronous 下逐条自动提交会把 5000 条拉到 10 秒级，指标失真（第一版踩过）。
